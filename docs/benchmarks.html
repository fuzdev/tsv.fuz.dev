benchmarks #

tsv is a Rust toolchain for parsing and formatting TypeScript/JS, CSS, and Svelte. Its formatter closely follows Prettier and borrows its architectural patterns, and we're grateful for the hard work of Prettier's contributors. After correctness, tsv prioritizes performance and efficiency: this page measures its speed and size on real-world code, and the conformance page compares parser coverage on deliberately hard test suites.

This page compares tsv to Prettier and the JS parsers it can replace (Svelte's and acorn-typescript), and to Oxc and Biome, similar tools with more features, configurable styles, and wider language support. It also measures rsvelte, yuku-parser, swc, dprint, Malva, and PostCSS; Language support lays out what each parses and formats.

tldr
#

tsv formats its three languages faster than Oxc and Biome in every in-process pairing here, and its CLI outpaces theirs in every shared scenario. Its artifacts are smaller than theirs too, except against oxc-parser's native build, since tsv publishes no native parse-only build yet. Theirs carry more languages and features.

Except in the CLI section, every timing here is in-process and one file at a time, isolating engine speed from multi-core parallelism. The corpus is 3,651 files of real-world code, the author's own and Svelte's (see Corpus), timed under Node v24.

  • Formatting TypeScript, tsv is ~2.4x faster than Oxfmt (native-vs-native), ~39x faster than Prettier (native Rust vs Prettier's JS; ~28x as wasm), and ~9.0x faster than Biome (wasm-vs-wasm).
  • Formatting Svelte, tsv is ~80x faster than Prettier (~56x as wasm) and ~12x faster than Biome (wasm-vs-wasm).
  • Formatting CSS, tsv is ~3.9x faster than Oxfmt (native-vs-native), ~117x faster than Prettier (~81x as wasm), and ~14x faster than Biome (wasm-vs-wasm).
  • Parsing TypeScript to its span-only AST (offsets only, like Oxc's), tsv is natively ~1.4x faster than oxc-parser's default JSON output (see Parse speed), and ~2.3x slower than yuku-parser (~2.8x as wasm). Its default AST adds per-node line/column loc for drop-in acorn and Svelte compatibility, at ~2.1x the span-only time: ~1.7x faster than acorn-typescript, the parser it can replace, but slower than Oxc and swc.
  • Parsing Svelte, that default AST is ~2.5x faster than svelte/compiler (JS) and ~2.3x faster than rsvelte (native-vs-native).
  • Parsing CSS runs the other way: Svelte's own parseCss is ~1.7x faster than tsv's default AST and PostCSS ~1.7x faster (see Parse speed - Svelte's is lower fidelity).
  • End to end as a CLI, tsv formats the JSX-free subset of a real TypeScript repo ~1.5x faster than Oxfmt and ~4.0x faster than Biome (~2.6x and ~6.9x as the bare binary, without Node in front), using less memory than either. These are wall-clock ratios, so they include each tool's multi-file parallelism (see the CLI section).
  • On a third-party Svelte corpus, tsv's CLI, again through its Node bin, is ~2.8x faster than rsvelte-fmt, another Rust Svelte formatter.

Nothing grades output against an oracle: the bench checks that output is non-empty and that tsv's native and wasm builds agree byte for byte. tsv's own output is checked against Prettier's in its repo's conformance gates.
  • Every tool that takes a filename gets a synthetic one (file.ts, file.css, file.svelte), so every row, Prettier's included, formats the corpus's .js files as TypeScript. A real Prettier run would hand .js to its Babel parser; which way that moves Prettier's time is unmeasured.

  • Biome has no dedicated Svelte formatter: its Svelte row runs with html.experimentalFullSupportEnabled, the experimental HTML-superset pipeline that formats the markup, script, and style. Its rows also carry two extra costs. The only format entry point in its in-process API (@biomejs/js-api), formatContent, opens the file in its workspace, pulls syntax diagnostics, and closes it on every call. And the harness periodically swaps in a fresh wasm instance, whose first sweep is slower. There's no native Biome entry: that API runs only on Biome's wasm builds, and the native engine ships only as the biome CLI, which the CLI section times.
  • The dprint entry is dprint-plugin-typescript, the engine deno fmt runs for TypeScript and JS, loaded in-process as its wasm plugin. It formats only TypeScript and JS, JSX included, so it has no Svelte row and its CSS slot goes to Malva, a third-party CSS plugin for the same host.
  • rsvelte-fmt, the other Rust-native Svelte formatter here, is grayed out in the Svelte group: the harness runs it over every Svelte file to check coverage but doesn't time it, since it ships no in-process API and a process per file would measure spawn rather than formatting. The CLI section times it.

Parse speed
#

tsv and oxc-parser, in its default mode, share a mechanism: both serialize the AST to JSON in Rust and hand it to the JS engine's JSON.parse, native and wasm alike. What they deliver differs, so tsv is timed three ways:

  • json (tsv json / tsv-wasm json) is tsv's default output. Every node carries a loc (line/column) object, which oxc-parser's span-only AST omits. On the TypeScript corpus it takes ~2.1x the time of the same parse without loc.
  • no-locs drops loc, giving a span-only AST of Oxc's kind. It is the closest comparison with oxc-parser but not an equal one: Oxc's AST also writes out default-valued fields tsv omits (optional: false, decorators: [], typeAnnotation: null), about 30% more bytes, and its parse also collects comments and module records.
  • internal builds tsv's AST in Rust and stops: no serialization, nothing materialized in JS. These entries show raw engine speed. Their gap to the json entries is what serializing and handing off costs tsv, not a cross-tool comparison.

yuku-parser, a JS/TS parser written in Zig, emits the same span-only AST as Oxc, so it too compares against the no-locs entries. It hands JS a compact binary buffer that decodes into objects when its program is read, so the bench reads it to time the same fully materialized result. swc's AST (a Module root with span offsets) matches neither of tsv's outputs.

Notes:

  • Every formatter is installed from npm, pinned by the fork's lockfile. The other tools are timed through their packages' Node bins, so tsv has two rows wherever it faces them. tsv via Node dispatcher is the like-for-like row: the Node bin of @fuzdev/tsv, which is what npx tsv runs once it's installed. That bin is a small Node script, the dispatcher, which launches the native binary, as Biome's and rsvelte-fmt's bins do. The plain tsv row runs the same binary directly from the platform package, skipping Node: what the binary costs on its own, the bare binary.
  • prettier + oxc-parser is Prettier with @prettier/plugin-oxc, which swaps in Oxc's Rust parser while printing stays in JS.
  • tsv, Oxfmt, Biome, and rsvelte-fmt parallelize across files; Prettier's stable CLI formats them one at a time (its worker pool comes with --experimental-cli, which the harness leaves off). No tool's thread count is pinned, so the wall-clock ratios bake in each tool's parallelism, scale with core count, and mean little apart from this machine.
  • The CPU ratio column compares hyperfine's user plus system time, summed across threads and child processes. It is the parallelism-neutral view, but only a rough proxy for engine speed: it also counts work other than formatting, enough that even Prettier's CPU time exceeds its wall-clock time.
  • tsv's dispatcher adds a fixed ~31 ms over the bare binary. Most of that is Node's own startup (a bare node -e "" takes ~19 ms on this machine), which every other npm-bin row pays too. As a share, that makes the dispatcher row ~2.9x the binary's time on the delivery table's one file but ~1.7x on the TypeScript repo. It adds little CPU beside the repo's multi-threaded work: in CPU time tsv leads Oxfmt ~2.0x through the dispatcher and ~2.1x as the bare binary; in wall-clock time, ~1.5x and ~2.6x.
  • @fuzdev/tsv-wasm takes ~9.4x the binary's time and ~8.7x its memory on the delivery table's one file. In time that is still well ahead of both Prettier rows in the single-file table but behind Oxfmt and Biome.
  • As the bare binary tsv uses 7.1–22x less peak memory than every other tool in every scenario; through its dispatcher, 1.9–9.3x less, though that row shows Node's peak, not the binary's. Peak memory is peak RSS, measured in a separate pass without warmups, with as many runs as the timed one. It is the largest single process in each command's tree, not the sum, so the rows that launch a native binary from Node (Biome, rsvelte-fmt, and tsv through its dispatcher) are understated.
  • As in the in-process charts, every formatter is pinned to tsv's fixed style in its own option dialect, so these rows aren't comparable with upstream's published numbers, which leave the tools nearer their defaults.
  • Before timing, a preflight run of each tool's check mode asserts that every formatter parses every file, that those reporting a file count report the same one, and that each finds at least one file to change, so a mis-scoped tool formatting nothing can't post an unbeatable time.
  • hyperfine runs commands in the order given, with no interleaving or shuffling, so on a machine that throttles, the later commands run hotter; a 10 s idle before each formatter's warmups narrows that, without removing it. Every scenario runs tsv's two rows last, the dispatcher row and then the bare binary, so thermal drift counts against tsv, not for it.

Cross-runtime
#

The same harness runs under three JS runtimes: Node, Deno, and Bun. The in-process charts above are the Node run, chosen as the default N-API host, not for speed. The native entry differs by runtime: Node and Bun load tsv's N-API addon; Deno loads its C-ABI library (the (ffi) build), which shares the addon's code but crosses a different binding boundary and is built differently. So a per-runtime delta on the same row comes from the JS engine, the host's N-API implementation, or that binding and build, not from tsv's algorithms.

The internal rows cross the binding boundary but materialize nothing on the JS side, so a delta there is the boundary plus each engine's hand-off of the source string into it, and for the wasm rows each engine's wasm compiler; the JSON-materializing parse rows add each JS engine's JSON.parse cost on top.

Times are per sweep: one full pass over the group's timed file set, as in the charts above. Ratios are relative to node, negative when slower. The other tools' native rows are their npm N-API addons under all three runtimes.

A ≈ marks a delta inside the two measurements' combined noise: read it as parity. The check has two limits. The slowest rows have too few timings for it, so an unmarked delta there isn't necessarily an effect. And it can't see variance between whole runs.

Benchmarking details
#

Each row is the mean time per sweep, a pass over its group's timed file set. Within a group every tool is timed on the same files — the intersection of what every timed tool accepted, so a file one rejects drops out for everyone. The count above each chart is that intersection, and a chart that runs short of the corpus total says beneath it what was left out and which rows failed it.

These are warm numbers: every row runs warmup sweeps before it is timed, so a cold one-shot call pays more. Each native or wasm call also pays a string encode across the binding boundary, and a decode wherever it hands back text or JSON, which the JS tools skip.

Each row is timed until it has both a few seconds of sweeps and at least 8 sweeps (16 for each group's reference row), so the slow rows stop at that floor. After outlier cleaning, rows keep from 6 to 1,665 timings. A steady reading over a handful of sweeps is thinner evidence than one over hundreds, so the harness's check for unstable rows proves less for the slow rows: Prettier, the default anchor of every format chart, and most of the TypeScript parse rows, tsv's included.

Rows run in a fixed order, not interleaved or shuffled: the reference row, then tsv's rows, then the alternatives. A forced garbage collection before each row limits what one row leaves for the next, but nothing pins the process to a core or holds the laptop CPU's clock steady, so whatever remains, thermal drift included, falls on the later rows. That bias favors tsv against every alternative but counts against it relative to the reference row, which runs first. The bias hasn't been measured directly, though no row's timings shift more than 3% from its first half to its second.

One asymmetry isn't isolated. Oxfmt's programmatic format is async-only, so each call's timing includes an N-API task dispatch and a promise resolution that tsv's sync call doesn't pay. (Prettier's is async-only too, without the N-API hop.) Oxfmt's native work may also run off the JS thread: still one file at a time, since each call is awaited before the next, but not strictly one thread.

Corpus
#

Every in-process timing on this page comes from 3,651 .svelte, .ts/.js, and .css files of real-world code, vendored in the fuzdev/corpora@446268f snapshot so one clone reproduces it. They're the author's libraries, apps, and sites (the fuz.dev ecosystem plus personal SvelteKit projects), and upstream framework source (Svelte, SvelteKit, and the svelte.dev site).

  • The snapshot's community Svelte libraries and tooling are left out: they would dominate the Svelte set. The CLI section's Svelte corpus draws on them.
  • Test files count as real code and stay in. Fixture files (formatter test suites, and fixture subtrees inside the measured repos) are out: deliberately tricky edge cases measure conformance, not typical throughput, and the conformance page covers them.
  • Standalone CSS files are rare in this ecosystem, so the CSS set adds the <style> blocks of the corpus's Svelte components, concatenated per corpus collection — 20 of its 55 entries. Even so, CSS is the weakest sample, with just 35 standalone files.
  • The corpus is the author's own code plus Svelte's, the same code tsv is developed and tested against and mostly tsv-formatted already. Input already in a tool's own style may format faster, which would favor tsv. Read every ratio here as "on this corpus", not as a universal figure.
