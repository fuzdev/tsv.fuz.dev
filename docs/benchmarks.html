benchmarks #

tsv is a Rust toolchain for parsing and formatting TypeScript/JS, CSS, and Svelte (source code). Its formatter closely follows Prettier and borrows its architectural patterns, and we're grateful for the hard work of Prettier's contributors. After correctness, tsv prioritizes performance and efficiency: this page measures its speed and size on real-world code, and the conformance page compares parser coverage on edge-case test suites.

This page compares tsv to Prettier and the JS parsers it can replace (Svelte's and acorn-typescript), and to Oxc and Biome, similar tools with more features, configurable styles, and wider language support, and, as a CLI only, Bun's built-in formatter (bun fmt). It also measures rsvelte, yuku-parser, swc, dprint, Malva, markup_fmt, and PostCSS; Language support lays out what each parses and formats.

tldr
#

tsv formats its three languages faster than Oxc and Biome in every in-process pairing here, and its CLI outpaces theirs using less memory in every shared scenario. Its artifacts are smaller than theirs too, except against oxc-parser's native build, since tsv publishes no native parse-only build yet.

Except in the CLI section, every timing here is in-process and one file at a time, isolating engine speed from multi-core parallelism. The corpus is 8,223 files of real-world third-party code: framework source, community libraries, CSS frameworks, and widely benchmarked TypeScript (see Corpus), timed under Node v24.

  • Formatting TypeScript, tsv is ~2.3x faster than Oxfmt (native-vs-native), ~48x faster than Prettier (native Rust vs Prettier's JS; ~26x as wasm), and ~8.2x faster than Biome (wasm-vs-wasm).
  • Formatting Svelte, tsv is ~123x faster than Prettier (~59x as wasm) and ~12x faster than Biome (wasm-vs-wasm), and rsvelte currently has no in-process API.
  • Formatting CSS, tsv is ~4.0x faster than Oxfmt (native-vs-native), ~117x faster than Prettier (~71x as wasm), and ~12x faster than Biome (wasm-vs-wasm).
  • Parsing TypeScript to its default span-only AST (offsets only, like Oxc's), tsv is natively ~1.5x faster than oxc-parser's default JSON transfer, but ~2.4x slower than its raw transfer (7% instability) and ~2.5x slower than yuku-parser (~3.7x as wasm; see Parse speed). With {locations: true}, which adds acorn's per-node line/column loc, it is ~1.3x faster than acorn-typescript, the parser it can replace, and still ahead of oxc-parser's JSON path and swc, whose ASTs carry none.
  • Parsing Svelte with {locations: true}, whose loc is a superset of Svelte's own, tsv is ~2.2x faster than svelte/compiler (JS) and ~3.1x faster than rsvelte (native-vs-native); its default span-only AST is ~2.9x faster than svelte/compiler.
  • Parsing CSS runs the other way, largely because Svelte has a lower fidelity CSS AST which tsv parses to more spec-faithful granularity: Svelte's own parseCss is ~1.8x faster than tsv's default parse, and PostCSS ~1.6x faster (see Parse speed). Under Bun it flips: tsv's default parse leads parseCss by ~2.0x, with parseCss ~1.7x slower there than under Node.
  • End to end as a CLI, tsv formats the JSX-free subset of a real TypeScript repo ~1.5x faster than Oxfmt and ~3.0x faster than Biome (~2.7x and ~5.4x as the bare binary, without Node in front), using less memory than either. These are wall-clock ratios, so they include each tool's multi-file parallelism (see the CLI section).
  • On a third-party Svelte corpus, tsv's CLI, again through its Node bin, is ~3.1x faster than rsvelte-fmt, another Rust Svelte formatter.
  • Bun's built-in formatter runs as a native executable with no Node in front, so it faces the bare binary: tsv is ~1.7x faster on the TypeScript repo, about even on the large single file, and ~2.6x faster on the Svelte corpus.

Drift is a change in a row's cost while it was being measured, which the cleaned coefficient of variation (cv) cannot see. Negative drift means the row got faster (still warming up); positive, slower (degrading). Pass spread is how far the row's passes, each timed in a fresh process, sat apart: a level that depends on the process. The mean published for such a row may sit between two levels.

Notes:

  • Each format row times the tool's own parse too: source in, formatted text out. Wasm-vs-wasm and native-vs-native (N-API here) are the like-for-like pairings, and the tsv-wasm rows run the full parse+format build, not the smaller format-only or parse-only ones.
  • Every formatter is pinned to tsv's fixed style (width 100, tabs, single quotes, no trailing commas) in its own option dialect, so each row does comparable layout work; the harness spot-checks the pins at startup. Nothing grades output against an oracle: the bench checks that output is non-empty and that tsv's native and wasm builds agree byte for byte. tsv's own output is checked against Prettier's in its repo's conformance gates.
  • Every tool that takes a filename gets a synthetic one (file.ts, file.css, file.svelte), so every row, Prettier's included, formats the corpus's .js files as TypeScript. A real Prettier run would hand .js to its Babel parser; which way that moves Prettier's time is unmeasured.
  • Oxfmt formats TypeScript, JS, and CSS with its own native engine but delegates Svelte to its bundled Prettier and prettier-plugin-svelte: only the embedded <script> reaches its native engine, while the markup, its expressions, and the <style> are that Prettier's.
  • Biome has no dedicated Svelte formatter: its Svelte row runs with html.experimentalFullSupportEnabled, the experimental HTML-superset pipeline that formats the markup, script, and style. Its rows also carry two costs beyond formatting: formatContent, the only format entry point in its in-process API (@biomejs/js-api), opens the file in its workspace, pulls syntax diagnostics, and closes it on every call; and since that workspace frees no memory, the harness swaps in a fresh wasm instance before every TypeScript and Svelte sweep (every few on CSS), at a few percent of each sweep. There's no native Biome entry: that API runs only on Biome's wasm builds, and the native engine ships only as the biome CLI, which the CLI section times.
  • The dprint entry is dprint-plugin-typescript, the engine deno fmt runs for TypeScript and JS, loaded in-process as its wasm plugin. It formats only TypeScript and JS, JSX included, so its CSS slot goes to Malva, a third-party CSS plugin for the same host, and its Svelte slot to markup_fmt (next).
  • markup_fmt, Malva's author's markup plugin for the same host, formats Svelte, handing each component's script, style, and template expressions to the dprint and Malva plugins. It isn't timed: it rejects valid Svelte this corpus holds, chiefly a quoted style attribute whose value isn't a declaration list (a map component's style prop holding a URL, which it parses as CSS) and some inline arrow-function event handlers. Every file a timed row rejects leaves every row's timed set, so timing it would drop whole example and docs pages from every Svelte number on this page. The harness checks its coverage instead.
  • rsvelte-fmt, the other Rust-native Svelte formatter here, is grayed out in the Svelte group: the harness runs it over every Svelte file to check coverage but doesn't time it, since it ships no in-process API and a process per file would measure spawn rather than formatting. The CLI section times it.

Parse speed
#

The parsers here don't return the same output, so each ratio compares different amounts of work. They differ in how much position data each node carries (offsets only, or loc too), in how finely they break down CSS (parseCss and PostCSS keep more of it coarse than tsv does), and in what they collect beyond the tree (Oxc also gathers comments and module records). Each tool is compared against tsv's closest output, and the notes cover what still differs.

tsv and oxc-parser, in its default mode, share a mechanism: both serialize the AST to JSON in Rust and hand it to the JS engine's JSON.parse, native and wasm alike. tsv is timed three ways:

  • tsv / tsv-wasm is what the parsers return by default: a span-only AST (start/end offsets, no loc) of Oxc's kind. It is the closest comparison with oxc-parser but not an equal one: Oxc's AST also writes out default-valued fields tsv omits (optional: false, decorators: [], typeAnnotation: null), about a third more bytes, and its parse also collects comments and module records.
  • +locations passes {locations: true}: the same parse with a loc (line/column) object on every node, rebuilt in JS from the offsets. That is acorn's shape on TypeScript, and on Svelte and CSS a superset of what their reference parsers carry. On the TypeScript corpus it takes ~1.2x the time of the default.
  • internal builds tsv's AST in Rust and stops: no serialization, nothing materialized in JS. These entries show raw engine speed. Their gap to the default entries is what serializing and handing off costs tsv, not a cross-tool comparison.

oxc-parser-raw is the same native Oxc parse and the same tree, handed to JS through Oxc's experimental raw transfer instead: a shared buffer that generated JS deserializes into objects before the call returns, skipping the JSON. tsv ships no such path. Oxc supports it natively only, and not under Bun.

yuku-parser, a JS/TS parser written in Zig, emits the same span-only AST as Oxc, so it too compares against tsv's default entries. It hands JS a compact binary buffer that decodes into objects when its program is read, so the bench reads it to time the same fully materialized result. swc's AST (a Module root with span offsets) matches neither of tsv's outputs.

Under Bun, tsv overtakes parseCss; the Cross-runtime section has the per-runtime numbers. The CSS corpus is also the page's weakest sample (see Corpus), so those ratios are the least representative.
  • Biome is grayed out across all three parse groups: its in-process API exposes no parse call, and the wasm workspace beneath it returns the syntax tree only as strings, not an AST to materialize and time. oxc-parser and swc are grayed out in the CSS group: Oxc formats CSS (in Oxfmt) and swc ships CSS tooling (@swc/css, which minifies and transforms), but neither ships a CSS parse binding.
  • oxc-parser's wasm row runs an older release than its native row, so the wasm-vs-wasm pairing crosses Oxc versions (both listed under Benchmarking details).
  • rsvelte's parser shares tsv's mechanism, a JSON string the caller JSON.parses, but delivers Svelte's own AST: loc on the acorn-parsed nodes plus name_loc. So rsvelte-parse compares against the +locations entries, whose loc on every node is a superset of it, rather than the span-only default. Its second entry passes rsvelte's own skipExpressionLoc, which drops loc from every JS node but keeps name_loc and the comments' loc, so it sits near tsv's span-only output without matching it. rsvelte also has parseEnvelope, a binary path that skips the JSON, untimed here since it drops the leadingComments that parse returns. Its addon targets its own upstream Svelte, 5.57.1, a release apart from the 5.57.3 the svelte/compiler row runs (both are listed under Benchmarking details).
  • PostCSS is the base of Prettier's CSS parse, so it's the parse-side counterpart of the Prettier format entry; none of the Rust CSS tools here exposes a parse call. Its payload doesn't match tsv's: it keeps selectors as strings where parseCss and tsv parse them.

Notes:

  • Every formatter is installed from npm, pinned by the fork's lockfile. Every other tool except Bun's formatter is timed through its package's Node bin, so tsv has two rows wherever it faces them. tsv via Node dispatcher is the like-for-like row: the Node bin of @fuzdev/tsv, which is what npx tsv runs once it's installed. That bin is a small Node script, the dispatcher, which launches the native binary, as Biome's and rsvelte-fmt's bins do. The plain tsv row runs the same binary directly from the platform package, skipping Node: the bare binary.
  • bun-fmt is Bun's built-in formatter, bun fmt, configured from the Prettier row's config. It runs as the Bun executable itself, with no Node in front, so its counterpart is the bare tsv binary rather than the dispatcher row the tables highlight. Against the bare binary, tsv is ~1.7x faster on the TypeScript repo, about even on the large single file, and ~2.6x faster on the Svelte corpus, using ~1.6x–4.1x less memory.
  • prettier + oxc-parser is Prettier with @prettier/plugin-oxc, which swaps in Oxc's Rust parser while printing stays in JS.
  • tsv, Oxfmt, Biome, rsvelte-fmt, and Bun's formatter parallelize across files; Prettier's stable CLI formats them one at a time (its worker pool comes with --experimental-cli, which the harness leaves off). No tool's thread count is pinned, so the wall-clock ratios bake in each tool's parallelism, scale with core count, and mean little apart from this machine.
  • The CPU ratio column compares hyperfine's user plus system time, summed across threads and child processes. It is the parallelism-neutral view, but only a rough proxy for engine speed: it also counts work other than formatting, enough that even Prettier's CPU time exceeds its wall-clock time.
  • tsv's dispatcher adds a fixed ~30 ms over the bare binary, most of it Node's own startup (a bare node -e "" takes ~19 ms on this machine), which every other npm-bin row pays too. It adds little CPU beside the TypeScript repo's multi-threaded work: in CPU time tsv leads Oxfmt there ~1.9x through the dispatcher and ~2.0x as the bare binary.
  • Peak memory is peak RSS, measured in a separate pass without warmups, with as many runs as the timed one. It is the largest single process in each command's tree, not the sum, so the rows that launch a native binary from Node (Biome, rsvelte-fmt, and tsv through its dispatcher) are understated.
  • As in the in-process charts, every formatter is pinned to tsv's fixed style in its own option dialect, so these rows aren't comparable with upstream's published numbers, which leave the tools nearer their defaults.
  • Before timing, a preflight run of each tool's check mode asserts that every formatter parses every file, that those reporting a file count agree, and that each finds at least one file to change, so a mis-scoped tool formatting nothing can't post an unbeatable time.

This section ran on November 7, 2026, from its harness at bbac542, on the same machine and Node as the in-process runs (12 threads). The versions of the tools both sections time are listed under Benchmarking details; its native tsv rows run the @fuzdev/tsv-linux-x64-gnu binary, and its wasm row @fuzdev/tsv-wasm 0.8.1.

Minified JS compresses much better than tsv's wasm, so beside it these entries look smaller by gz than by raw bytes.
  • dprint (wasm), Malva (wasm), and markup_fmt (wasm) expose no parser, so all three sit under Formatter beside tsv's format-only wasm build. That build does Svelte, TypeScript/JS, and CSS in one artifact; Malva formats CSS and its dialects only, dprint TypeScript/JS and JSX only, and markup_fmt the markup of Svelte and other template languages, which needs the other two loaded beside it for a component's script and style.
  • Biome's build carries its whole toolchain: parsers, formatters, and linters across the languages it supports, plus assists like import sorting, GritQL search and plugins, and a module graph. yuku-parser parses TypeScript, JS, JSX, and TSX only, where tsv's parse-only build beside it carries Svelte and CSS parsers too. Oxfmt ships no wasm build, hence its grayed-out slot under Formatter.

Cross-runtime
#

The same harness runs under three JS runtimes: Node, Deno, and Bun. The in-process charts above are the Node run, chosen as the default N-API host, not for speed. The native entry differs by runtime: Node and Bun load tsv's N-API addon; Deno loads its C-ABI library (the (ffi) build), which shares the addon's code but crosses a different binding boundary and is built differently. So a per-runtime delta on the same row comes from the JS engine, the host's N-API implementation, or that binding and build, not from tsv's algorithms.

The internal rows cross the binding boundary but materialize nothing on the JS side, so a delta there is the boundary, each engine's hand-off of the source string into it, and for the wasm rows each engine's wasm compiler. The parse rows that materialize JSON add each engine's JSON.parse on top, and the +locations rows the JS walk that rebuilds loc.

  • bun — oxc-parser-raw
These rows are unmeasured there, so a gap in those columns is a load failure rather than a speed result.
⚠ Some measurements were not stable, so every ratio through them is unreliable:
  • node — parse/typescript/oxc-parser-raw (cv 3.9%, raw cv 4.2%, drift +4.1%, pass spread 6.8%)
  • deno — parse/css/svelte/compiler (cv 3.1%, raw cv 3.3%, drift +0.2%, pass spread 6.0%)
  • bun — parse/typescript/tsv-wasm (cv 4.0%, raw cv 4.0%, drift +0.5%, pass spread 9.5%)
  • bun — parse/typescript/oxc-parser-wasm (cv 3.1%, raw cv 3.1%, drift +5.6%, pass spread 0.5%)
Drift is a change in a row's cost while it was being measured (negative: still warming up; positive: degrading); pass spread is how far the row's passes, each a fresh process, sat apart. Each such cell is marked ⚠ below; read its ratio as unmeasured until that runtime is re-run.

Times are per sweep: one full pass over the group's timed file set, as in the charts above. Ratios are relative to node, negative when slower. The other tools' native rows are their npm N-API addons under all three runtimes. A fail means that runtime has no number for the row: either it can't load the implementation (listed above when the report records it), or its report doesn't carry the row.

A ≈ marks a delta inside the two measurements' combined noise: read it as parity. The check has two limits. Each side's noise is the spread of a row's few passes, each a fresh process, which is a thin estimate, so an unmarked delta near it isn't necessarily an effect. And it can't see variance between whole runs.

Benchmarking details
#

Each row is the mean time per sweep, a pass over its group's timed file set. Within a group every tool is timed on the same files — the intersection of what every timed tool accepted, so a file one rejects drops out for everyone. The count above each chart is that intersection, and a chart that runs short of the corpus total says beneath it what was left out and which rows failed it.

These are warm numbers: every row runs warmup sweeps before it is timed, so a cold one-shot call pays more. Each native or wasm call also pays a string encode across the binding boundary, and a decode wherever it hands back text or JSON, which the JS tools skip.

tsv's native rows time the build it ships: profile-guided (PGO), trained by running the build itself over the author's own code, which the timed corpus leaves out. Its wasm rows are not profile-guided.

Each row is timed in 3 passes, and each pass runs until it has both a few seconds of sweeps and at least 8 sweeps, so the slow rows stop at that floor in every pass. After outlier cleaning, rows keep from 20 to 2,726 timings across their passes. A steady reading over a few dozen sweeps is thinner evidence than one over hundreds, so the harness's check for unstable rows proves less for the slow rows, those that ran fewer than twice the floor's sweeps. Prettier, every format chart's default anchor, is among them in each format group:

  • Format Svelte: prettier, oxfmt, biome-wasm
  • Format TypeScript/JS: every row
  • Format CSS: prettier
  • Parse Svelte: svelte/compiler, tsv+locations, tsv-wasm+locations, rsvelte-parse, rsvelte-parse-skip-expr-loc
  • Parse TypeScript/JS: acorn-typescript, tsv, tsv-wasm, tsv+locations, tsv-wasm+locations, oxc-parser, oxc-parser-wasm, oxc-parser-raw, yuku-parser, yuku-parser-wasm, swc

Every pass of every row runs in a fresh process that loads that row's tool and nothing else, so no tool's code, garbage, or warmed-up state is shared with the next. Each pass takes a group's rows in a different order (forward, reversed, then rotated), so no row always runs right after the same one, and a row's number is the average of its passes. What no process boundary removes is the machine: nothing pins the process to a core or holds the laptop CPU's clock steady. Two fresh processes of the same row sat 1% apart at the median and 3% at the 95th percentile in this run, so a ratio inside that isn't a difference the run measured. A row whose passes sat 5% or more apart is flagged as unstable, and no row's timings shift more than 5% from the first half of a pass to its second.

One asymmetry isn't isolated. Oxfmt's programmatic format is async-only, so each call's timing includes an N-API task dispatch and a promise resolution that tsv's sync call doesn't pay. (Prettier's is async-only too, without the N-API hop.) Oxfmt's native work may also run off the JS thread: still one file at a time, since each call is awaited before the next, but not strictly one thread.

Corpus
#

Every in-process timing on this page comes from 8,223 .svelte, .ts/.js, and .css files of real-world code, vendored in the fuzdev/corpora@dce40bd snapshot so one clone reproduces it. They're upstream framework source (Svelte, SvelteKit, and the svelte.dev site), community Svelte libraries and tooling (Bits UI, shadcn-svelte, Skeleton, Flowbite Svelte, Svelte Flow, Threlte, Runed, LayerChart, Layer Cake, Svelte UX, svelte-maplibre, and Svelte's language tools), CSS frameworks (daisyUI and Open Props), and TypeScript other formatter benchmarks compare on (TypeScript's own parser, Storybook, and Continue).

None of it is the author's own code. The snapshot vendors that too, but tsv's native builds are profile-guided, trained on exactly those collections (see Benchmarking details), so it's held out of every timing here rather than flattering them.

  • Test files count as real code and stay in. Fixture files (formatter test suites, and fixture subtrees inside the measured repos) are out: deliberately tricky edge cases measure conformance, not typical throughput, and the conformance page covers them.
  • Standalone CSS files are rare in Svelte code — most of its CSS lives in components — so the CSS set is the standalone .css files plus the <style> CSS of every measured .svelte file, harvested into one stylesheet per corpus collection — 9 of its 192 entries:
    • each component's top-level <style> block is taken verbatim — :global(…) and all — minus the indent it carried inside the tag; empty blocks and non-CSS langs (SCSS, PostCSS) are skipped
    • a collection's blocks are joined into one file, so its size is however much CSS that repo wrote — large files that measure throughput more than per-call overhead
    • nothing is filtered for validity: like every perf file, each tool must take each stylesheet, and one a tool rejects leaves every row's timed set (Biome refuses the ones carrying Svelte's leading-combinator :global(> …))
    • the same bytes are timed again inside the Svelte rows — rows are never summed, so nothing counts twice
    Even so, CSS is the weakest sample, with just 183 standalone files.
  • Read every ratio here as "on this corpus", not as a universal figure.
